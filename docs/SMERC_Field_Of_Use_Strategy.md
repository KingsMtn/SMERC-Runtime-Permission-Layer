# SMERC Field Of Use Strategy

## Purpose

This note keeps SMERC from being unintentionally treated as a single AWS-only asset.

AWS/cloud action governance is the current enterprise proof path, but SMERC is broader than AWS. Commercial planning should separate:

1. SMERC Core
2. field-specific implementation packages
3. rights reserved for future verticals

This is strategic planning language, not legal advice. Any actual sale, license, acquisition, exclusivity, or field-of-use agreement should be reviewed by qualified IP and licensing counsel before signature.

## SMERC Core

SMERC Core should be treated as the underlying platform IP.

It includes:

- recoverability-before-execution
- posture vocabulary: `ALLOW`, `THROTTLE`, `FREEZE`, `DENY`, `ESCALATE`
- recoverability scoring
- Runtime Evidence Trust Gate
- hard admission and evidence gates
- Governance Routing Workbench / SPARTa route controls
- Decision Lifecycle Ledger
- postcondition evidence
- autonomy health, budgeting, earned autonomy, and continuance concepts
- metadata-only reviewer model
- action momentum, blast-radius, rollback-latency, evidence-validity, and containment reasoning
- `smerc.decision.v1` and related reusable decision-language contracts

SMERC Core should not be presumed sold, transferred, assigned, exclusively licensed, or field-restricted merely because one vertical package gets commercial traction.

## First Commercial Wedge: AWS / Cloud Action Governance

The current first enterprise wedge is AWS-style cloud action governance.

This field includes:

- AWS-style agent action chains
- Bedrock/Lambda-shaped decision handlers
- AgentCore-style runtime and gateway patterns
- IAM, Systems Manager, CloudFormation, CloudWatch remediation, S3, RDS, ECS/Fargate, cost-velocity, Secrets Manager, and cross-account delegation examples
- AWS metadata intake
- AWS shadow mirror metadata
- AWS postcondition evidence
- cloud automation and infrastructure-change review

Commercial discussions in this lane should be framed as an AWS/cloud field package unless the conversation explicitly prices and negotiates all SMERC fields.

## Reserved Future Fields

SMERC should preserve optionality in other fields, including:

- SMERC-F: financial actions, stablecoin, crypto, treasury, payments, tokenized assets, wallet-policy changes, and automated financial operations
- insurance: claims automation, underwriting assistance, fraud routing, risk scoring, payout controls, coverage changes, and automated policy operations
- healthcare and life-impact workflows: high-trust actions where reversibility, evidence, consent, and escalation matter
- CI/CD and DevOps: GitHub, GitLab, deployment, infrastructure-as-code, and release-governance workflows
- MCP and tool governance: MCP gateway, tool-call sessions, tool-definition integrity, delegated approval, and server/action boundaries
- enterprise security operations: remediation, quarantine, revocation, rotation, restore, and containment actions
- government or regulated operations: administrative actions where irreversible impact, due process, or auditability matter

These fields should remain available unless an agreement explicitly includes them.

## Deal Posture

Use this framing:

> SMERC Core is the recoverability governance framework. AWS/cloud is one field-specific implementation package. Rights for AWS/cloud should not imply rights to finance, insurance, crypto, healthcare, CI/CD, MCP/tool governance, security operations, or other SMERC fields unless those fields are explicitly included.

Avoid this framing:

- "AWS is SMERC."
- "Selling the AWS package sells the whole platform."
- "A cloud buyer automatically gets SMERC-F."
- "One pilot field determines all future SMERC rights."

## Planning Rule

When building or discussing a new feature, classify it as one of:

- core reusable SMERC IP
- AWS/cloud field package
- financial/crypto/SMERC-F field package
- insurance field package
- CI/CD or DevOps field package
- MCP/tool-governance field package
- other future field package

If a feature is reusable across fields, document it as SMERC Core plus one or more field applications.

## Commercial Boundary

Public review, local non-production evaluation, and metadata-only critique do not grant production, hosted, embedded, resale, sublicensing, or revenue-generating rights.

Commercial use should specify:

- field of use
- exclusivity or non-exclusivity
- territory, if relevant
- duration
- sublicensing rights
- hosted-service rights
- derivative-work rights
- source-code access
- data/evidence ownership
- reserved fields
- treatment of SMERC Core improvements

## Work / Result / Impact

Work:

Separate SMERC Core from AWS/cloud and future vertical packages before serious commercial discussions begin.

Result:

An AWS opportunity can move forward without accidentally consuming financial, crypto, insurance, healthcare, CI/CD, MCP, or broader platform rights.

Impact:

SMERC preserves momentum from one successful field while keeping the broader recoverability governance platform available for later licensing, partnership, acquisition, or vertical expansion.
