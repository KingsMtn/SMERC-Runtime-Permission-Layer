# SMERC Two-Tier Valuation Path

## Purpose

This page explains how SMERC can support a two-tier valuation story without overclaiming.

The blunt answer is yes: SMERC can move toward two different value layers, but only if the public standard and the enterprise implementation are kept distinct.

## Tier 1: Public Decision Language And Review Standard

Tier 1 is the open, inspectable layer.

It includes:

- `smerc.decision.v1`
- posture terms: `ALLOW`, `THROTTLE`, `FREEZE`, `DENY`, `ESCALATE`
- safe metadata-only action inputs
- conformance checks
- reviewer quickstarts
- public reports
- no-secrets evidence boundaries
- customer-owned metadata replacement path

Work:

Make SMERC easy for AI assistants, open-source reviewers, cloud teams, MCP implementers, and security architects to understand, run, and reference.

Result:

The project becomes a reusable decision-language and proof format for recoverability-aware agent governance.

Impact:

This layer can create credibility, search visibility, ecosystem vocabulary, external feedback, and adoption pressure. It is not enough by itself for a large acquisition value because anyone can read public concepts and large companies may build internal variants.

## Tier 2: Enterprise Cloud Action Governance Package

Tier 2 is the implementation and buyer-specific proof layer.

It includes:

- AWS-style metadata adapter
- Bedrock/Lambda-shaped decision handler
- cloud action-chain replay
- postcondition evidence
- performance metrics
- Decision Lifecycle Ledger
- customer-owned metadata evaluation
- shadow-mode pilot plan
- commercial-use boundary
- deployable bot readiness path

Work:

Package SMERC as a recoverability-aware action governor for agentic cloud automation, especially high-consequence cloud actions where IAM, guardrails, logs, and approval workflows do not fully answer whether an authorized action is still recoverable enough to execute.

Result:

A serious platform reviewer can see where SMERC fits: after content/model guardrails and identity checks, before consequential execution, with postcondition evidence after the route.

Impact:

This is the stronger acquisition path because it converts SMERC from an interesting public standard into a working enterprise control pattern that could reduce risk for cloud platforms, AI-agent platforms, security platforms, and infrastructure teams.

## Why The Two Layers Matter

The public layer helps others learn the language.

The enterprise layer shows why a company might want the implementation, evidence chain, and integration model instead of only copying terms.

If the public layer grows without the enterprise layer, SMERC risks becoming a vocabulary artifact.

If the enterprise layer grows without the public layer, SMERC risks becoming a private demo that nobody can evaluate.

The valuation path needs both:

1. public credibility through inspectable standards and runnable examples
2. strategic value through enterprise-grade proof, integration shape, and pilot evidence

## Evidence Needed For A Higher Strategic Valuation

SMERC does not reach a serious two-tier valuation because the idea is clever. It gets there by accumulating proof.

The premortem in `docs/SMERC_Premortem.md` should be used as a check against overbuilding the wrong proof. It lists warning signals that would show whether the project needs tighter framing, more concrete packaging, real reviewer metadata, or a different first buyer.

Required proof:

- one-command public AWS-style replay
- strict no-secrets metadata intake
- conformant decision-language output
- postcondition evidence showing controls happened
- p50 and p95 local overhead metrics
- customer-owned metadata substitution path
- reviewer labels showing whether posture recommendations were useful
- at least one external design-partner or strategic technical review signal
- clear commercial-use terms for organizations that implement SMERC in products

## Current Status

Tier 1 status:

Started and credible. SMERC has public language, decision contracts, examples, conformance checks, reviewer docs, and machine-readable review assets.

Tier 2 status:

Started, not finished. SMERC has AWS-style action-chain proof, metadata intake, postcondition evidence, performance reporting, and reviewer bundle artifacts. It still needs external metadata replacement, reviewer labels, and a bounded shadow-mode pilot signal.

## Next Build Order

1. Keep `smerc.decision.v1` stable enough that outside tools can emit it.
2. Keep AWS as the main enterprise proof path.
3. Add AWS-style decision-language output to every serious AWS report.
4. Pair each posture with postcondition evidence and timing metrics.
5. Ask reviewers for 5 to 25 metadata-only actions from one real workflow.
6. Convert reviewer feedback into a shadow-mode pilot package.

## Language To Use

Use this:

> SMERC has a two-layer value path: an open recoverability decision language that others can inspect and a cloud-action governance package that proves how the language becomes enterprise runtime control.

Avoid this:

- "SMERC is already worth millions."
- "AWS will buy this."
- "This is an official standard."
- "This is production-ready."
- "This replaces cloud security controls."

## Bottom Line

The best path is not to split SMERC into a consumer product right now.

The best path is to make the public standard easy to reference while making the AWS-style implementation hard to dismiss.
